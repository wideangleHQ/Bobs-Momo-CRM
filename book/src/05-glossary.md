# Glossary

Definitions here are local. Several of these words mean something else in other systems,
and where that is true it is called out in the definition. When a chapter uses one of
these terms, it means what this page says it means.

## Business terms

| Term | Definition as used in this system |
|---|---|
| QSR | Quick service restaurant. A counter-service food outlet with fast order turnaround, no table service and two heavy demand peaks per day. The operating pattern, not the cuisine, is what drives the design: nothing gets entered into the system between 12:00 and 14:00 or between 18:00 and 21:00 |
| Outlet | One physical restaurant location, modelled as `Outlet` with a unique `code` such as `BM-SAHEED` or `BM-PATIA`. The outlet is the primary scoping boundary for almost all operational data. Stock, tasks, shifts, purchases and sales all belong to exactly one outlet |
| Department | A grouping inside an outlet: Kitchen, Counter, Store or Admin. Modelled as `Department`, unique per outlet by name. Tasks and broadcasts can be addressed to a department, so "Kitchen at Patia" is an addressable audience |
| Trading day | The human description of one day of operation, from opening prep around 07:00 to close around 23:30, including the paperwork that lands after midnight. The system's machine-readable version of this is the business date |
| Business date | A calendar date in Asia/Kolkata, stored as `@db.Date`, that a record belongs to operationally. Stored on `StockTransaction`, `AttendanceDay`, `Task`, `Shift`, `DailySalesEntry` and `Purchase`. It is not the same as the row's `createdAt` timestamp, which is UTC and records when the row was written |
| Business-day boundary | 04:00 Asia/Kolkata. Any timestamp from 00:00 to 03:59 IST resolves to the previous calendar date as its business date. A closing checklist submitted at 00:30 on Sunday belongs to Saturday. Implemented once, in the helper described in chapter 12 |
| Opening stock | The counted quantity of an item at an outlet at the start of a business day, recorded as a `StockTransaction` of type `OPENING`. It is a counted fact, not a carry-forward calculation, which is why a mismatch against yesterday's closing balance is meaningful information rather than an error |
| Closing stock | The counted quantity at the end of the business day, recorded as type `CLOSING`. The difference between closing stock and the running balance the ledger predicted is the outlet's shrinkage for the day |
| Restock | Stock arriving at the outlet from a vendor. Recorded as type `RECEIVED`, normally created automatically by recording a purchase rather than entered by hand |
| Issue | Moving stock from the outlet store room into the kitchen for use. Recorded as type `ISSUED`. This is the local meaning and it is the one that matters: an issue is a stock movement, not a support ticket and not the creation of a work item. When a chapter says "issue 5 kg of mince", it means the store handed it to the kitchen |
| Wastage | Stock lost rather than used: spoiled, dropped, burnt, expired. Recorded as type `WASTAGE`, and `reason` is required on the row. Wastage feeds the waste analysis report and is the one stock type where the reason text is read by a human later |
| Adjustment | A correction to the stock ledger, recorded as type `ADJUSTMENT` with a required reason. Because the ledger is append-only, this is the only way to fix a wrong entry. There is no edit and no delete |
| Indent | The kitchen or store word for a request for stock to be bought in. In this system an indent for something the outlet does not have becomes a `PurchaseRequest`. An indent for something already in the store room is not a system object at all, it is just an `ISSUED` transaction |
| Reorder level | The per item per outlet threshold below which the system raises `LOW_STOCK`. Stored on `ItemStock.reorderLevel` and nullable. Null means no alert for that item at that outlet |
| SOP | Standard operating procedure. A written routine such as fryer cleaning or fridge temperature checks. SOPs have no table of their own. They are `ChecklistTemplate` rows, executed through the task engine like every other checklist |
| Opening checklist | The morning routine run before service: gas, fridge temperatures, hygiene, stock board, till float. A `ChecklistTemplate` with `code` `KITCHEN_OPEN`, run as a `Task` of kind `CHECKLIST_RUN` generated by a `TaskRecurrence` |
| Closing checklist | The end of service routine: shutdown, cleaning, wastage recording, cash count. Same mechanism as the opening checklist, different template |
| Audit | An inspection-style checklist where results are graded rather than just ticked. A `ChecklistTemplate` with `isAudit` true, run as a `Task` of kind `AUDIT_RUN`. Each item is recorded `PASS`, `FAIL` or `NA`, and a `FAIL` on an item flagged `failCreatesTask` generates a follow-up task linked by `parentTaskId`. Not to be confused with the audit log |
| Audit log | The system-wide record of who changed what, stored in `AuditLog`. Append-only. Different concept from an operational audit and the two are never mixed |
| Roster | The published schedule of who works which shift at which outlet. Modelled as `Shift` rows. Replaces the forwarded WhatsApp image the business uses today |
| Shift | One scheduled block of work for one employee on one date, with `startsAt` and `endsAt`. A shift is a plan. Attendance is what actually happened. The two are compared, never conflated |
| Attendance day | One row per employee per business date, `AttendanceDay`, holding the derived status, first in, last out and worked minutes. Individual punches hang off it as `AttendancePunch` rows |
| Break | A logged pause inside a shift, `BreakLog`, with a start, an optional end and a computed duration. Break minutes are subtracted from worked minutes during the nightly rollup |
| Comp off | Compensatory time off. Leave granted for having worked on a scheduled weekly off or a holiday. Modelled as `LeaveType.COMP_OFF`. Phase 1 records it and does not compute the entitlement that produced it |
| CTC | Cost to company. The total monthly employment cost including basic and allowances, stored on `SalaryRecord.monthlyCtc`. Phase 1 stores this figure. Nothing computes a payslip from it |
| GSTIN | Goods and Services Tax Identification Number, the fifteen character Indian tax registration id. Stored on `Vendor.gstin` as free text for invoice reference. It is not validated and nothing in Phase 1 files a tax return |
| UPI | Unified Payments Interface, the dominant instant payment rail in India. Appears only as `DailySalesEntry.upiAmount`, one figure in the daily payment split. The system never touches a payment |

## System terms

| Term | Definition as used in this system |
|---|---|
| Outbox | The `OutboxEvent` table. A business write that needs to notify someone inserts an outbox row inside the same database transaction as the write. A cron dispatcher then picks up `PENDING` rows and turns them into notifications. This guarantees that the notification exists if and only if the business change committed |
| Event key | The stable upper snake case string identifying what happened, such as `LOW_STOCK` or `TASK_OVERDUE`. The same string appears on `OutboxEvent`, `Notification` and `NotificationPreference`. Fourteen exist and the list is closed |
| Idempotency key | A client-generated value sent in the `Idempotency-Key` header on `POST /purchases`, `POST /inventory/transactions` and `POST /attendance/punch`. The server stores the key with its response in Redis for 24 hours and replays the stored response on a repeat. It exists because staff on a weak mobile connection tap submit twice |
| Refresh token rotation | Every use of a refresh token issues a new one and revokes the old. All tokens descended from one login share a `familyId`. If a revoked token is presented again, the whole family is revoked, which is how a stolen token is detected. Refresh tokens are stored as a SHA-256 hash, never in plaintext |
| RBAC | Role-based access control. Each `User` holds exactly one `roleKey` from the nine in `RoleKey`, and the role determines which permission keys they hold. There are no per-user permission grants in Phase 1 |
| Permission key | A string in the form `module.resource.action`, lowercase and dot separated, such as `inventory.transaction.create`. Checked by `PermissionsGuard` against the role's permission set. Every endpoint declares exactly one |
| Outlet scope | The second half of an access check, enforced by `OutletGuard`. `ALL_OUTLETS` means the user sees every outlet and belongs to `OWNER` or `OPERATIONS_MANAGER` only. `OWN_OUTLET` limits the user to outlets listed in `UserOutlet`. `SELF` appears on workforce endpoints so a staff member can read and write their own attendance, breaks, leave and tasks without seeing anyone else's. A resource outside your scope returns 404, not 403 |
| Soft delete | Setting `isActive` to false instead of removing the row. The row stays queryable, history stays intact, and foreign keys stay valid. The only hard deletes in the system are `RefreshToken` rows and cascade children |
| Ledger | An append-only sequence of rows describing what happened, in order, where a row is never updated and never deleted. `StockTransaction` is the stock ledger. `AuditLog` and `OutboxEvent` are also append-only. A correction is always a new row |
| Running balance | The current derived quantity, `ItemStock.qtyOnHand`, kept in step with the ledger inside the same transaction that writes the ledger row. Every `StockTransaction` also stores `balanceAfter`, so the balance at any past point can be read directly instead of recomputed by summing |
| Signed quantity | `StockTransaction.signedQty`. The row also stores `quantity`, which is always positive, and `signedQty`, which carries the direction after the sign rules for the transaction type are applied. `RECEIVED` is positive, `ISSUED` and `WASTAGE` are negative, and the balance is the sum of signed quantities |
| Deep link | The in-app URL stored on `Notification.deepLink` that takes the recipient straight to the thing the notification is about, such as the specific task or leave request. A notification without a deep link makes the recipient hunt for the record, which is the failure mode this field exists to prevent |
| Broadcast | A one-to-many message from a manager to an outlet or a department, modelled as a `Message` with `scope` of `OUTLET` or `DEPARTMENT`. It is stored in the system of record and can also be delivered over WhatsApp. Distinct from a notification, which is generated by an event rather than composed by a person |
| Digest | A batched notification that collects several events into one message on a schedule instead of sending one message per event. Phase 1 uses this for low stock, through the low stock digest job, so that a delivery arriving short on six items produces one message rather than six |
| Cooldown | The minimum gap before the same alert fires again for the same subject. `ItemStock.lastAlertAt` implements it for low stock, so an item hovering near its reorder level does not alert on every issue |
| Request id | The short correlation id returned on every error response and written to the logs. When a user reports a failure, this is the string that finds the log line |

## Stack terms

| Term | Definition as used in this system |
|---|---|
| NestJS module | A class decorated with `@Module` that groups a controller, a service, a repository and their providers for one business domain. One folder under `apps/api/src/modules`, one domain, the same file set every time |
| Controller | The HTTP surface of a module. Parses and validates the request, applies guards and the permission decorator, calls the service, returns the result. Contains no business rules and no Prisma calls |
| Service | Where business rules and transaction boundaries live. Multi-step writes, such as recording a purchase and receiving the stock, are wrapped in one `prisma.$transaction` here. If a rule is described in this book, it is enforced in a service |
| Repository | The only place Prisma is called from within a module. Takes and returns typed objects, holds no business logic, and exists so that services stay testable and query shapes stay in one place |
| Guard | A class implementing `CanActivate` that runs before the route handler and decides whether the request proceeds. Three matter here: `JwtAuthGuard` for authentication, `PermissionsGuard` for the permission key, `OutletGuard` for outlet scope |
| Interceptor | A class that wraps the handler and can act on the request or the response. `AuditInterceptor` writes the `AuditLog` row for state-changing calls. `TransformInterceptor` applies the response envelope |
| Pipe | A transformation and validation step on an incoming value. `ZodValidationPipe` parses the request body against the shared zod schema and rejects with a 400 and a field-level detail list on failure |
| DTO | Data transfer object. In this codebase a DTO is a zod schema plus its inferred TypeScript type, defined in `packages/shared` so that the API and the web app validate against the same definition |
| Prisma schema | `apps/api/prisma/schema.prisma`, the single source of truth for the database. Models, enums, relations, indexes and constraints all live here. Chapter 10 is its documentation |
| Migration | A generated, numbered SQL file under `prisma/migrations`, applied in order and never edited after it has run anywhere. Migrations are forward only in this project |
| Prisma client | The generated, typed query client. Injected through `PrismaService`, which is a `PrismaClient` subclass wired into Nest lifecycle hooks |
| Prisma transaction | `prisma.$transaction`, used for every multi-step write. When a diagram in this book draws a transaction boundary, it means one of these, and a failure at any step inside it rolls back everything in it |
| Next.js App Router | The routing model used by the web app, where directories under `app/` define routes and components are server components unless marked otherwise |
| Server component | A React component rendered on the server with no client JavaScript shipped for it. Used for the read-heavy list and detail pages. Cannot use hooks or browser APIs |
| Client component | A component marked `"use client"`, shipped to the browser. Used for forms, anything interactive and anything using TanStack Query |
| Route handler | A server-side endpoint inside the Next.js app, used for the small number of things that must run on the web tier rather than calling the NestJS API directly. Business logic does not go here |
| TanStack Query | The client-side data layer, version 5. Owns fetching, caching, refetching and mutation state for client components. Every list view that a manager watches during service relies on its refetch behaviour |
| Supabase | The managed PostgreSQL 15 host, on the Pro plan, providing the database, daily backups with seven day retention, and object storage |
| Supavisor | Supabase's connection pooler. The API connects through it rather than directly to Postgres, because a platform that scales container instances will otherwise exhaust the connection limit |
| Supabase Storage | The object store used for task proof photos. Objects are referenced by `TaskAttachment.storageKey`, and files are never stored in the database |
| Upstash Redis | The managed Redis instance on a fixed 250MB plan, reached over TCP with the ioredis client. Used for caching dashboard summaries and published game configuration, for rate limiting, and for idempotency key storage. It is a cache, so nothing in it is the system of record |
| Railway | The application host. Two services in one project: the NestJS API and the Next.js web app. Hobby plan, in line with the under Rs 5,000 per month infrastructure target |
| Node 22 and Bun | Production runs Node.js 22 LTS. Bun stays in the repository for local development scripts and tests, so `bun install`, `bun test` and `bun run` are the local commands. The reasoning is recorded in ADR-002 in chapter 07 |
