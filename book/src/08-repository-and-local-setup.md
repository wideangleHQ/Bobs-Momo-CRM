# Repository layout and local setup

One repository, three workspaces, one lockfile. This chapter covers where code
goes, how to get the whole thing running on a laptop, and what to do when it
does not start.

What belongs where, and what does not.

`apps/api/src/common` holds anything wired into the global request pipeline or
injected everywhere. If it is used by exactly one module, it belongs in that
module, not here. `common` is not a junk drawer.

`apps/api/src/modules/<name>` holds one business domain. A module never reaches
into another module's `repository`. It injects the other module's `service`.
Cross-module writes happen through a service that owns the transaction.

`apps/api/src/jobs` holds cron job classes only. A job is a thin wrapper: it
resolves a service and calls one method. Business logic in a job file is a
review rejection, because logic in a job cannot be reached from a test that
does not fake the scheduler.

`apps/api/prisma/migrations` is generated by `prisma migrate dev`. Never edit a
migration that has been applied anywhere other than your own laptop. Fix it
forward with a new migration.

`apps/web/components/ui` is shadcn output. Edit these freely, they are ours
now, but keep the diff from upstream small enough to re-apply a future version.

`packages/shared` contains zod schemas, the types inferred from them, and
enums. It imports nothing from `apps/*`, contains no React, no Nest decorators
and no Prisma types. Its `dependencies` list is one entry long: `zod`. If
somebody adds a second, ask why in review.

## The per-module file set

Every backend module has the same six kinds of file.

```text
modules/inventory/
  inventory.module.ts          providers, imports, exports. Wiring only.
  inventory.controller.ts      REST surface. Routes, guards, DTO binding.
  inventory.service.ts         Business rules. Owns $transaction boundaries.
  inventory.repository.ts      Prisma calls. One method, one query shape.
  dto/
    create-item.dto.ts         re-exports the zod schema from shared
    record-transaction.dto.ts
  inventory.service.spec.ts    unit tests, repository mocked
  inventory.e2e-spec.ts        supertest against a real test database
```

Two rules make this layering worth having.

Controllers do no business logic. A controller method reads the decorated user,
passes the validated DTO to a service method, and returns the result. No `if`
statements about business state, no Prisma import, no date arithmetic. If you
find yourself writing a conditional in a controller, the condition belongs in
the service.

Repositories do no business logic. A repository method builds and runs one
query and returns rows. It does not decide whether stock is sufficient, does
not compute a signed quantity, and does not throw domain errors. It accepts an
optional Prisma transaction client so the service can compose several
repository calls inside one `$transaction`.

```ts
// inventory.repository.ts
async findStockForUpdate(tx: Prisma.TransactionClient,
                         itemId: string, outletId: string) {
  const rows = await tx.$queryRaw<ItemStockRow[]>`
    SELECT * FROM item_stock
     WHERE item_id = ${itemId}::uuid AND outlet_id = ${outletId}::uuid
     FOR UPDATE`;
  return rows[0] ?? null;
}
```

The service decides what a null row means. The repository just says there is no
row.

## Local setup

### Prerequisites

| Tool | Version | Check |
|---|---|---|
| Bun | 1.1.30 or newer | `bun --version` |
| Node.js | 22.x LTS | `node --version` |
| Docker Engine | 24 or newer | `docker --version` |
| Docker Compose | v2 plugin | `docker compose version` |
| Git | 2.40 or newer | `git --version` |
| psql client | 15 or newer, optional | `psql --version` |

Node is required even though Bun runs the scripts. Prisma's CLI and the
production build both run on Node, and CI runs the e2e suite on Node 22.

### Clone and install

```bash
git clone git@github.com:wideanglemedia/bobs-momo.git
cd bobs-momo
bun install
```

`bun install` resolves all three workspaces from the root `package.json`. Do not
run `bun install` inside `apps/api`. It will create a second `node_modules` and
you will spend an hour on a duplicate-Prisma-client error.

### Start Postgres and Redis

The file is committed at the repository root.

```yaml
# docker-compose.yml
services:
  postgres:
    image: postgres:15-alpine
    container_name: bobs-momo-pg
    restart: unless-stopped
    environment:
      POSTGRES_USER: bobsmomo
      POSTGRES_PASSWORD: localdev
      POSTGRES_DB: bobsmomo
      TZ: Asia/Kolkata
    ports:
      - "54322:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U bobsmomo -d bobsmomo"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7-alpine
    container_name: bobs-momo-redis
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "no", "--save", ""]
    ports:
      - "63790:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
```

Ports 54322 and 63790 are deliberately not the defaults. Most engineers already
have something on 5432 and 6379, and a silent connection to the wrong database
is worse than a refused connection.

```bash
docker compose up -d
docker compose ps          # both services should read "healthy"
```

### Create the environment files

```bash
cp .env.example apps/api/.env
cp apps/web/.env.example apps/web/.env.local
```

Then edit `apps/api/.env` so the connection details match the compose file. The
full variable reference is in
[Environments and configuration](09-environments-and-configuration.md).

```bash
DATABASE_URL="postgresql://bobsmomo:localdev@localhost:54322/bobsmomo?schema=public"
DIRECT_URL="postgresql://bobsmomo:localdev@localhost:54322/bobsmomo?schema=public"
REDIS_URL="redis://localhost:63790"
JWT_ACCESS_SECRET="paste 64 hex characters here"
JWT_REFRESH_SECRET="paste different 64 hex characters here"
WHATSAPP_ENABLED=false
NODE_ENV=development
PORT=3001
```

Generate the two secrets with `openssl rand -hex 32` and paste the output. They
must differ from each other.

Locally `DATABASE_URL` and `DIRECT_URL` are identical because there is no
pooler in front of the container. In staging and production they differ. See
ADR-004.

### Migrate and seed

```bash
cd apps/api
bunx prisma generate
bunx prisma migrate dev
bunx prisma db seed
cd ../..
```

`prisma migrate dev` applies every migration in `prisma/migrations` and
regenerates the client. `prisma db seed` runs `prisma/seed.ts`, which creates
two outlets (`BM-SAHEED`, `BM-PATIA`), their departments, the nine roles from
`RoleKey`, one user per role, about 40 inventory items across five categories,
six units, three vendors, two checklist templates and 30 days of backdated
stock transactions so the dashboard has something to draw.

Seeded logins are printed at the end of the seed run. The default password is
`ChangeMe123!` and every seeded user has `mustReset = true`.

### Run both apps

```bash
bun run dev
```

That runs both workspaces concurrently from the root. To run them separately in
two terminals:

```bash
bun run --cwd apps/api dev      # NestJS, watch mode, port 3001
bun run --cwd apps/web dev      # Next.js, turbopack, port 3000
```

URLs that come up:

| URL | What it is |
|---|---|
| `http://localhost:3000` | Next.js app, redirects to `/login` |
| `http://localhost:3001/api/v1/health/healthz` | liveness, returns `{"status":"ok"}` |
| `http://localhost:3001/api/v1/health/readyz` | checks Postgres and Redis |
| `http://localhost:5555` | Prisma Studio, after `bunx prisma studio` |

## Verification checklist

Six checkpoints. Work through them in order. Each one tells you which layer is
broken if it fails.

Checkpoint 1. `docker compose ps` shows both containers `healthy`. If Postgres
is `starting` for more than 30 seconds, `docker compose logs postgres` usually
shows a volume permission problem or a port clash.

Checkpoint 2. `bunx prisma migrate status` from `apps/api` prints "Database
schema is up to date". If it prints drift, your local database does not match
`migrations/`, and the fix is `bunx prisma migrate reset` unless you have data
you care about.

Checkpoint 3. `curl -s localhost:3001/api/v1/health/readyz | jq` returns
`{"status":"ok","db":"up","redis":"up"}`. If `db` is `down` the API cannot reach
Postgres, which is almost always a wrong port in `DATABASE_URL`. If `redis` is
`down` and `db` is `up`, only `REDIS_URL` is wrong, and the app will still work
for everything except caching and rate limiting.

Checkpoint 4. `http://localhost:3000/login` renders the login form with no
console errors. A blank page with a hydration error usually means `apps/web`
picked up a stale `.next` directory. Delete it and restart.

Checkpoint 5. Log in as the seeded owner. You land on the dashboard and see
non-zero numbers for both outlets. Zero numbers everywhere means the seed did
not run, not that the dashboard is broken.

Checkpoint 6. Record a stock issue of 1 KG against any item at BM-SAHEED. The
stock list updates without a page refresh and a new row appears in the
transaction history. This exercises the full path from ADR-008: guards,
validation, `$transaction`, materialised balance, cache invalidation and
TanStack refetch. If this works, your environment is correct.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `P1001: Can't reach database server at localhost:54322` | Postgres container not running, or wrong port in `DATABASE_URL` | `docker compose up -d postgres`, then confirm the port is 54322 not 5432 |
| `ERROR: prepared statement "s0" already exists` | Pooled `DATABASE_URL` missing `pgbouncer=true` | Add `?pgbouncer=true&connection_limit=1` to the pooled URL. Staging and production only |
| `PrismaClientInitializationError: the table does not exist` after editing `schema.prisma` | Client regenerated but migration not applied | `bunx prisma migrate dev --name <change>` from `apps/api` |
| `PrismaClientValidationError: Unknown arg` right after a schema change | Generated client is stale | `bunx prisma generate`, then restart the dev server |
| `EADDRINUSE: address already in use :::3000` | Another Next.js or a stale process holds the port | `lsof -ti:3000 \| xargs kill -9`, or `PORT=3005 bun run --cwd apps/web dev` |
| `argon2` build failure on `bun install`, `node-gyp` errors | No C toolchain, or Node headers missing for the installed version | Install `build-essential` and `python3`, then `bun install --force`. On Alpine add `libc6-compat` |
| Browser console: `blocked by CORS policy` calling `:3001` from `:3000` | `CORS_ORIGINS` does not list the web origin | Set `CORS_ORIGINS=http://localhost:3000` in `apps/api/.env` and restart the API |
| Every request returns 401 with `JWT malformed` right after editing `.env` | `JWT_ACCESS_SECRET` changed, existing tokens signed with the old one | Clear site data in the browser and log in again. Tokens do not survive a secret rotation |
| `Drift detected: your database schema is not in sync` | A migration was edited after being applied, or the DB was changed by hand | `bunx prisma migrate reset` locally. Never run reset against staging or production |
| `Unique constraint failed on the fields: (code)` during seed | Seed run twice against a non-empty database | `bunx prisma migrate reset` which drops, migrates and reseeds in one step |
| `ECONNREFUSED 127.0.0.1:63790` on boot | Redis container down or wrong port in `REDIS_URL` | `docker compose up -d redis`. The API boots without Redis but logs a warning on every cache call |
| `Nest can't resolve dependencies of the InventoryService (?)` | A provider is missing from the module's `providers` array, or a circular import | Add the provider. For a genuine cycle use `forwardRef()` and leave a comment saying why |
| Login succeeds then every request 403s | Seeded user has no `UserOutlet` row and is not OWNER | Reseed, or insert the `UserOutlet` row. `OutletGuard` denies a user with empty scope |
| Dashboard numbers do not change after a write | Cache key not invalidated on that write path | Check the `RedisService.del` call in the service. As a workaround, `FLUSHDB` on the local Redis |

## Git conventions

### Branch naming

`<type>/<ticket>-<short-slug>`, all lowercase, hyphens not underscores.

```text
feat/BM-142-stock-transfer-between-outlets
fix/BM-198-negative-balance-on-wastage
chore/BM-203-bump-prisma-6-2
docs/BM-211-rbac-matrix
```

`main` is protected. Nothing lands without a pull request and one approval.
There is no `develop` branch. Three weeks is too short for a release train.

### Commit format

Conventional Commits: `type(scope): description`.

Types are `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `perf`, `build`.

Scopes for this repository:

```text
auth        users       outlets     employees   attendance
shifts      leave       salary      inventory   purchase
vendors     tasks       sales       analytics   notifications
whatsapp    messaging   crm         web         shared
prisma      ci          config
```

```text
feat(inventory): add TRANSFER_OUT and TRANSFER_IN paired transactions
fix(attendance): treat a punch before 04:00 as the previous business day
refactor(purchase): move price history write into PurchaseService
test(tasks): cover overdue sweep across the business day boundary
chore(prisma): add index on outbox_event(status, availableAt)
```

The description is imperative and lowercase and does not end in a period. Body
paragraphs are optional. A `BREAKING CHANGE:` footer is required for any change
to an API response shape or an enum value, because the web app consumes both.

### Pull request template

`.github/pull_request_template.md` asks for six things.

What changed, in two or three sentences, written for somebody who has not read
the ticket.

Which ticket, as a link.

How it was tested: the commands run, and for a UI change a screenshot on a
375 px viewport, since that is where staff use it.

Schema impact: does this add a migration, and is it reversible without data
loss. If it drops or renames a column, say so in bold at the top.

Permission impact: which permission keys were added or changed, and which roles
gain access.

Rollback plan: one line. For most changes it is "revert the commit". For a
migration it is not, and that needs writing down before merge, not after.

### Definition of done

A ticket is done when all eight of these are true.

The code is merged to `main` and deployed to staging. Unit tests cover the
business rules in the service, including the failure path, not just the happy
path. An e2e test covers at least one route end to end if the ticket adds a
route. `bun run lint` and `bun run typecheck` pass with no new warnings. Any
new endpoint is documented in its module chapter with its permission key,
request shape, response shape and error codes. Any new `OutboxEvent.eventKey`
is added to the event table in chapter 21 in chapter 21. Any new permission key is added
to the RBAC matrix in chapter 14. The reviewer has run it locally, not only
read the diff.

Anything not on that list is not a blocker. Perfect naming, additional
refactoring and speculative test coverage are all things to raise as follow-up
tickets rather than hold a merge over.
